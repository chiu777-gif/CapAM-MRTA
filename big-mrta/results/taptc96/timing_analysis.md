# BiG-MRTA 与 ILS/EILS 的运行时间核验

结论：当前计时没有发现单位或取平均错误，但这些是不同实现的运行时间，不能当作论文原实现的速度比例复现。同一 TAPTC 96 场景上，BiG-MRTA 原版实际快于本地 EILS；较慢的是全任务适配版。

## 论文与本地实现

[CapAM 论文 Table II](https://arxiv.org/pdf/2205.03321) 报告的是完整任务分配序列的生成时间，对 96 个场景取平均：ILS 1.342 秒、EILS 0.992 秒、BiG-MRTA 0.301 秒。这个表格不规定其他语言、实现和适配协议下必须保持相同排序。

本地实现存在明确差异：

- **ILS/EILS**：依据文献重新实现的 C++ 求解器，`g++ -O3` 编译，预计算旅行/服务时间，缓存未发生变化的路线插入候选。Python 仅通过 ctypes 调用。见 [solver.py](../../../EILS/solver.py)、[solver.cpp](../../../EILS/solver.cpp) 和 [复现边界](../../../EILS/SOURCES.md)。没有取得 CapAM 论文实际使用的 ILS/EILS 实现及完整配置，不能声称复现了论文两项耗时。
- **BiG-MRTA 原版**：直接调用作者 Python/NetworkX 实现。每次决策遍历机器人和剩余任务，创建图及边，再转换为稀疏矩阵和密集矩阵，最后调用 SciPy 匹配。
- **BiG-MRTA 全任务适配版**：还包含空分配后的重试、所有任务覆盖，以及每一步公共 PyTorch 仿真器更新。它与原版的工作量和调度语义不同。

## 原来报告的结果

| 实现 | 单场景完整求解平均时间 |
|---|---:|
| ILS，按原始分组选择参数，C++ 单线程 | 55.017 ms |
| EILS，按原始分组选择参数，C++ 单线程 | 148.297 ms |
| BiG-MRTA 原版，线程设置 4 | 125.978 ms |
| BiG-MRTA 全任务适配版，线程设置 4 | 202.571 ms |

BiG 原版 / EILS = 0.8495；BiG 适配版 / EILS = 1.3660。因此原版并没有比 EILS 慢。另需避免拿 1000 个训练同分布场景的时间与原始 TAPTC 96 场景混比。

## 同一 CPU、统一单线程的补测

为了排除线程设置差异，重新对同一原始 96 场景运行四份现有实现：batch size=1、场景串行、每实现预热一个完整场景，每场景轮换算法执行顺序，每算法每场景运行一次。没有修改算法、搜索参数或停止条件；EILS 使用 group1=tight、group2=slack。计时包含求解器完整调用，排除数据读取/准备、编译、预热、验证和输出。

| 实现 | 96 场景总时间（秒） | 单场景平均（ms） | 按时完成任务数 |
|---|---:|---:|---:|
| ILS C++ | 5.043016 | 52.531 | 5734 |
| EILS C++ | 13.749093 | 143.220 | 5788 |
| BiG-MRTA 原版 | 11.288828 | 117.592 | 5389 |
| BiG-MRTA 全任务适配版 | 17.897603 | 186.433 | 5392 |

任务完成数全部与原报告一致。补测确认相同的相对排序：BiG 原版快于 EILS，适配版约慢 30%。这些仍然是当前实现及各自协议的实测，不是所有算法语义、实现语言和优化程度全部统一的算法效率实验。原版 BiG 允许不分配任务；其他三项包含全任务补全。单次测量的绝对时间会有运行波动，不覆盖原报告数值。

完整元数据和源码哈希见 [timing_benchmark.json](timing_benchmark.json)，逐场景记录见 [timing_benchmark.csv](timing_benchmark.csv)。

## BiG 的开销在哪里？

对 8 个代表场景（tight/slack × 2/3/5/7 个机器人各一个）做 cProfile 剖析：

| 函数 | 原版累计时间（秒） | 适配版累计时间（秒） |
|---|---:|---:|
| 全部剖析求解 | 1.421626 | 2.193571 |
| `getNextTask` 自身时间，不包含其调用函数 | 0.606221 | 0.661552 |
| NetworkX `add_edge` | 0.230996 | 0.210981 |
| `biadjacency_matrix` | 0.382592 | 0.543329 |
| 公共仿真器 `StateMRTA.update` | 不使用 | 0.493528 |
| SciPy `linear_sum_assignment` | 0.003756 | 0.004947 |

实际匹配求解器的剖析占比分别只有约 0.26% 和 0.23%；主要开销是 Python 循环、图对象、矩阵转换及适配版状态更新。剖析会改变程序耗时，这些数值只用于定位开销，不能代替上面的正常计时。各累计时间也不能任意相加，因为其中部分调用存在嵌套。详见 [timing_profile.json](timing_profile.json)。

原来适配版 202.571 ms 的正常计时中，`getNextTask` 调用累计为 142.935 ms，其余矩阵/状态构造、状态更新和包装等约为 59.636 ms。这部分同样计入完整解延迟；独立重放验证没有计入。

因此，不能将“当前 C++ EILS 比 Python BiG 适配版快”解读为 EILS 算法必然比 BiG 更快，也不能从论文的排序反推本地计时一定错误。需要区分原版与适配版，并同时报告实现语言、优化方式、停止条件和计时范围。
